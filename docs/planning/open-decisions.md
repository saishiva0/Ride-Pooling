## Resolved decisions

### OD-004 — Matching thresholds and ranking policy (resolved in Phase 3.19)

| Field                   | Resolution                                                                                                                                                                                                                                                                                                                                                                |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Status                  | **RESOLVED** (Phase 3.19)                                                                                                                                                                                                                                                                                                                                                 |
| Pickup search radius    | **5,000 meters** (participant pickup within this radius of the ride pickup). Inclusive at the boundary. Server-controlled.                                                                                                                                                                                                                                                |
| Departure time window   | **±60 minutes** (absolute difference between the participant's preferred departure and the ride departure ≤ 60 minutes). Inclusive at the boundary. Server-controlled.                                                                                                                                                                                                    |
| Destination tolerance   | **5,000 meters** (participant destination within this straight-line tolerance of the ride destination). Inclusive at the boundary. Server-controlled.                                                                                                                                                                                                                     |
| Numeric relevance score | **NOT USED in V1.** No score is computed or exposed. The deterministic, explainable factor results plus proximity ranking remain authoritative.                                                                                                                                                                                                                           |
| Ranking                 | 1. pickup distance ascending; 2. absolute departure-time difference ascending; 3. ride ID ascending (deterministic final tie-break). Never database row order, never random.                                                                                                                                                                                              |
| Maximum results         | **20.** Server-owned; callers cannot override it.                                                                                                                                                                                                                                                                                                                         |
| Matching explanations   | Structured factor results (`FactorResult`) produced by the matching domain: per-factor `eligible`, measured `value`, `threshold`, and a deterministic `reason`. Internal implementation details, DB records, private data, and imaginary weights are never exposed.                                                                                                       |
| Configuration           | Server-controlled configuration (env vars, defaults `5000` / `60` / `5000` / `20`). HTTP callers CANNOT supply thresholds, weights, ranking, score, or result limits — such input is rejected.                                                                                                                                                                            |
| Determinism             | Identical input + identical database state ⇒ identical ordering and results. No ML/AI ranking, no dynamic behavioral ranking, no external matching provider.                                                                                                                                                                                                              |
| OD-004 rationale        | The matching engine already provides deterministic, explainable factor results and proximity ranking (Phase 3.4). A weighted score would introduce arbitrary weighting without additional product evidence — V1 stays transparent and deterministic (ADR-007). Thresholds default from `matching-model.md` §6's validated range (5 km pickup, ±60 min, 5 km destination). |
| Implementation          | Phase 3.19 (backend + mobile). No schema changes, no new entities, no matching persistence. No changes to OD-007 / OD-008 / OD-010.                                                                                                                                                                                                                                       |

### OD-005 — Authentication method: phone + OTP via MSG91 (resolved in Phase 3.18)

| Field                         | Resolution                                                                                                                                                                                                                                                                                                                                                        |
| ----------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Status                        | **RESOLVED** (Phase 3.18)                                                                                                                                                                                                                                                                                                                                         |
| Authentication method         | Phone + OTP (SMS) — no email/password, no magic link, no social/external provider                                                                                                                                                                                                                                                                                 |
| OTP provider                  | MSG91 (SMS). Legacy SendOTP API (`api.msg91.com`): `sendotp.php`, `verifyRequestOTP.php`, `retryotp.php`                                                                                                                                                                                                                                                          |
| OTP delivery                  | SMS only; `retrytype=text` on resend (voice never used in V1)                                                                                                                                                                                                                                                                                                     |
| OTP verification ownership    | Backend-owned and backend-performed (MSG91 `verifyRequestOTP`); the client never receives or validates the OTP itself                                                                                                                                                                                                                                             |
| Phone identity                | E.164 international format (`+` prefix). India-focused default: a bare 10-digit number is treated as `+91…`; existing `normalizePhone` (Phase 3.9) remains the single normalization implementation                                                                                                                                                                |
| Session model                 | Backend-issued opaque bearer token (32 random bytes, base64url) per verified OTP. The DB stores only a SHA-256 hash of the token (`AuthSession.tokenHash`, `@unique`). Default TTL 30 days; no refresh tokens; logout revokes the presented session server-side; expired/revoked sessions are rejected                                                            |
| OTP policies                  | OTP length 6 (configurable 4–9); expiry 5 minutes (configurable 1–1440); request rate limit 3 per phone per 10 minutes; verify-attempt rate limit 5 per phone per 10 minutes (in-memory; documented single-instance limitation)                                                                                                                                   |
| Enumeration / leak protection | The backend returns a generic success for `request-otp` (no "already registered" difference); every authentication failure returns the same generic 401; MSG91 responses (including provider error messages) are never exposed to clients; MSG91 secrets are backend-only env vars (`MSG91_AUTH_KEY`, `MSG91_SENDER_ID`) and never inlined into the mobile bundle |
| Security constraints          | Constant-time OTP comparison happens inside the provider (MSG91); tokens are compared via SHA-256 hash lookup (no plaintext tokens persisted or logged); user existence is never disclosed; `name` on new users is an empty string until Phase 3.x profile editing                                                                                                |
| Provider failure              | MSG91 send/verify/retry failures map to `EXTERNAL_SERVICE_ERROR` (500/502-class, not exposed verbatim); a missing `MSG91_AUTH_KEY` fails closed (OTP cannot be requested/verified)                                                                                                                                                                                |
| OD-005 partial sub-decision   | OD-010 (verification requirements) remains OPEN for V1/V1.1; only the auth-handshake sub-part is resolved by this decision                                                                                                                                                                                                                                        |

### OD-007 — Map provider / geocoding / distance provider (resolved in Phase 3.20)

| Field                     | Resolution                                                                                                                                                                                                                                                                                                                                                                                           |
| ------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Status                    | **RESOLVED** (Phase 3.20)                                                                                                                                                                                                                                                                                                                                                                            |
| Provider                  | Google Maps Platform — maps, geocoding, and routes (Distance Matrix is not used; per-ride route distance/duration is computed by the Routes API).                                                                                                                                                                                                                                                    |
| Client-side (no backend)  | Geocoding and routing run directly from the mobile app against Google REST APIs with a public, Android/iOS-restricted API key (`EXPO_PUBLIC_GOOGLE_MAPS_API_KEY`). No backend proxy, SDK, or endpoints were added; the backend is untouched. Acceptable per spec §29 (client can resolve addresses/coordinates without server involvement).                                                          |
| Provider-neutral boundary | Mobile consumes the Google providers through the existing `GeocodingProvider` and new `RoutingProvider` ports (mirroring `LocationClient`). Screens/components receive providers via props; `createDefaultLocationDependencies()` (Phase 3.19) wires real vs. injected providers. The app never calls Google directly from UI code.                                                                  |
| Fail-closed default       | With no `EXPO_PUBLIC_GOOGLE_MAPS_API_KEY`, the default dependencies produce `unavailableLocationClient`, `failClosedGeocodingProvider`, and `failClosedRoutingProvider`. The map renders an explanatory placeholder; the app never fabricates coordinates/places/routes. All failures normalize to `MobileError` kinds (e.g. `external-service`, `network`, `timeout`, `not-found`, `rate-limited`). |
| Geocoding                 | Google Geocoding API. `ZERO_RESULTS` resolves to an empty result (not an error). Forward and reverse geocoding both supported and tested.                                                                                                                                                                                                                                                            |
| Routing                   | Google Routes API (`computeRoutes`) with `polylineEncoding=ENCODED_POLYLINE`. `decodePolyline` (Phase 3.12) converts the encoded polyline to `[lng, lat]` `LineString` coordinates for the map overlay. Duration is parsed from the `duration` string (`"602s"` → 602).                                                                                                                              |
| Distance in discovery     | Ride discovery distance remains backend-computed (Phase 3.3 PostGIS). Client-side routing is display-only (route preview); it never affects matching/discovery results.                                                                                                                                                                                                                              |
| Key restrictions          | Production key must be restricted to Android (package + SHA-1) and iOS (bundle ID) and HTTPS referrers; the key is a public client key and is never used server-side. Missing/restricted key fails closed in the app.                                                                                                                                                                                |
| Google Maps iOS note      | Google Maps on iOS requires a development build (custom dev client / prebuild) with the `react-native-maps` config plugin; it does not render in Expo Go. Android maps render in Expo Go.                                                                                                                                                                                                            |
| OD-007 rationale          | Google Maps Platform is the de-facto standard for India (OD-016 default geography), integrates with the existing `react-native-maps` map view, and avoids a second map SDK. Client-side REST keeps the backend unchanged and the mobile bundle self-contained for mapping.                                                                                                                           |
| Implementation            | Phase 3.20 (mobile only). New packages `react-native-maps` + `expo-location`; new components (`RidePoolMap`, `LocationSearch`, `LocationPicker`, `RoutePreview`); new hooks (`useGeocoding`, `useRoute`, `useMapLocation`); new providers (`google-geocoding-provider`, `google-routing-provider`). No schema changes, no backend changes, no matching/auth changes.                                 |

### OD-008 — Realtime transport and authentication mechanism (resolved in Phase 3.22)

| Field                    | Resolution                                                                                                                                                                                                                                                                                                                                                                                     |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Status                   | **RESOLVED** (Phase 3.22)                                                                                                                                                                                                                                                                                                                                                                      |
| Realtime transport       | Socket.io (Phase 3.11 architecture preserved). Single-process deployment for V1. No message broker (Redis/Kafka/NATS/RabbitMQ) in V1.                                                                                                                                                                                                                                                          |
| Authentication mechanism | Bearer token (opaque session token) — the same Phase 3.18 authentication system. Socket handshake passes `Authorization: Bearer <token>` header; the `HttpAuthenticator` validates via the session service. No separate socket auth mechanism.                                                                                                                                                 |
| Identity source          | Server-side only — `AuthenticatedUser` derived from successful bearer token validation. Client-supplied `userId` in handshake/query/headers is NEVER trusted.                                                                                                                                                                                                                                  |
| Room strategy            | Private, server-controlled rooms: `user:{userId}`. Joined only from authenticated identity. No client-controlled room joining.                                                                                                                                                                                                                                                                 |
| Connection lifecycle     | `connection` → authenticate → join room; `disconnect` → leave room. Structured logging (no credentials/tokens/OTP).                                                                                                                                                                                                                                                                            |
| Reconnection behavior    | Transient failures: bounded exponential backoff, max retries. Authentication failures (invalid/expired/revoked token): no retry, surface as auth error. Session-invalid errors: disconnect, clear session, surface to app. Duplicate connections prevented. Duplicate listeners prevented. Reconnection restores subscriptions. Missed events NOT fabricated — REST is the recovery mechanism. |
| Event semantics          | Seven events: `RIDE_REQUESTED`, `REQUEST_ACCEPTED`, `REQUEST_REJECTED`, `REQUEST_CANCELLED`, `RIDE_CANCELLED`, `RIDE_EXPIRED`, `RIDE_CONFIRMED`. Minimal payloads (identifiers + title/body). Never Prisma records, credentials, tokens, OTP, phone numbers, or internal IDs. Event IDs for client-side identification only (not persisted).                                                   |
| Delivery guarantee       | Best-effort realtime notification. Post-commit publish (transaction → commit → publish). Rollback → NO event. Persistent database notifications remain authoritative.                                                                                                                                                                                                                          |
| Duplicate-event handling | Stable subscription management. `subscribe`/`unsubscribe` lifecycle. Reconnect does not double-register. Event IDs available for diagnostics but no replay system.                                                                                                                                                                                                                             |
| Persistence relationship | Realtime is a delivery mechanism only. Database-backed notifications are the source of truth. Offline clients recover via `GET /api/v1/notifications`. No outbox, no event replay in V1.                                                                                                                                                                                                       |
| Offline behavior         | UI remains functional with local state. Realtime state not guaranteed. REST is recovery. Reconnect restores subscriptions; refreshes authoritative state where needed. No event replay protocol.                                                                                                                                                                                               |
| Scaling strategy         | V1: single-process Socket.io (in-memory adapter). Horizontal scaling (multiple instances) is post-V1 infrastructure — documented, not implemented. Socket.io Redis adapter would be the mechanism if/when needed.                                                                                                                                                                              |
| Security requirements    | Fail-closed auth. Server-derived identity. No caller-controlled recipient/room. Minimal payloads. No secrets in logs. Connection errors normalized. Reject arbitrary room joins. Auth spoofing prevented (identity from token only).                                                                                                                                                           |
| Operational logging      | Structured logs with safe metadata only. Connection events (auth success/failure, connect/disconnect/reconnect). Event delivery failures logged without payload details. No PII, tokens, OTP, or credentials.                                                                                                                                                                                  |
| Explicit V1 limitations  | Single-process only. Best-effort delivery (no exactly-once). No presence/typing/location streaming. No push notifications (Phase 3.23). No chat (deferred to V1.1 per OD-009). No outbox. No broker. No event replay. No multi-instance scaling.                                                                                                                                               |

### OD-008 — Push provider (resolved in Phase 3.23)

| Field                | Resolution                                                                                                                                                                                                                                                                                |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Status               | **RESOLVED** (Phase 3.23)                                                                                                                                                                                                                                                                 |
| Push provider        | Expo Notifications + Expo Push Service.                                                                                                                                                                                                                                                   |
| Platforms            | Android + iOS.                                                                                                                                                                                                                                                                            |
| SDK version          | Expo SDK 57.                                                                                                                                                                                                                                                                              |
| V1 approach          | Expo Push Service for V1.                                                                                                                                                                                                                                                                 |
| Provider abstraction | Provider-specific code remains behind `PushNotificationProvider` abstraction so FCM/APNs can replace Expo later without spreading Expo-specific code through ride/domain/navigation code.                                                                                                 |
| Device token model   | `DevicePushToken` — multiple devices per user, Android/iOS, Expo push token, platform, isActive, createdAt, updatedAt, lastSeenAt. Tokens belong to authenticated users; userId NEVER accepted from client.                                                                               |
| API endpoint         | `POST /api/v1/notifications/device-tokens` (registration), `DELETE /api/v1/notifications/device-tokens/:token` (deactivation). Authenticated; identity from middleware only.                                                                                                              |
| Lifecycle            | Permission → Expo token → backend registration (idempotent, updates lastSeenAt, reactivates). Refresh on token change. Logout attempts deactivation but succeeds even if cleanup fails. Invalid tokens deactivated after provider rejection.                                              |
| Push dispatch        | Integrated into existing notification creation flow: business event → recipient resolution → persisted notification → realtime notification → push notification (best-effort). Push failure NEVER rolls back ride/request operation. Partial device failure continues with other devices. |
| Payload              | Uses existing notification content (title, body, data). Data supports typed mobile navigation. No passwords, tokens, secrets, sensitive PII, stack traces.                                                                                                                                |
| Mobile module        | `apps/mobile/src/notifications/` — permissions (unknown/requesting/granted/denied/unavailable), Expo token acquisition, registration, token lifecycle, foreground handling, background handling, tap routing to existing typed navigation routes.                                         |
| Security             | Authenticated device registration, token ownership enforced, no caller-controlled recipient, no userId from client, no token/credential logging, no provider secrets in mobile, no sensitive push payloads, backend-only provider credentials, authorization on token operations.         |
| Environment          | Backend secrets backend-only. No `EXPO_PUBLIC_*` for push. Required config documented in `.env.example` files.                                                                                                                                                                            |
| Testing              | Backend tests cover registration, ownership, push dispatch, failure handling. Mobile tests cover permissions, token lifecycle, foreground/background, tap routing. Never contact Expo servers during tests — mock the provider boundary.                                                  |
